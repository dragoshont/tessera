# R2 Trusted-Local Plugin SDK

Plugin packages are trusted-local directories under the configured root. A package contains a UTF-8 manifest and optional non-secret configuration. A separate operator-owned catalog maps plugin ID/version to expected SHA-256 and is not writable through product APIs. The loader opens regular non-symlink files below the canonical root, reads bounded bytes once, verifies the catalog digest over those same bytes, and parses those bytes, preventing path traversal and manifest TOCTOU. Validation also requires strict semantic versions, supported minimum Tessera version, unique IDs, known executor kinds, typed JSON schemas, and no unknown security-sensitive fields.

First-party executable implementations are separate trusted-local `Tessera.Plugins.*` assemblies governed by ADR 0032. Broker discovers them through `Tessera.Plugin.Abstractions`; Broker, Core, execution, and jobs never reference implementation assemblies. The declarative package remains the installation, enablement, configuration, and historical-descriptor record. The executable module must match its plugin ID/version and may implement only capabilities declared by that record.

Each capability declares stable ID/version, description, input/output schemas, executor kind/configuration, account and permissions, allowed data classes, side-effect class, idempotency, verification, timeout, and max result bytes. Historical calls record plugin and capability versions. Disable removes availability immediately.

An executable first-party module contributes typed account hooks, capability factories, Chat/Job tool definitions and bindings, endpoint mappings, and hosted-service registration through the generic contract. It parses its own provider configuration from the generic host configuration source. Runtime policy still owns account grants, credential-reference resolution, egress authorization, approvals, execution, and evidence. Modules receive resolved generic context only for an authorized invocation and must not bypass those controls.

Assembly discovery is explicit and local. The host canonicalizes the operator-owned root, rejects symlinks and escapes, bounds the candidate set, and orders candidates by ordinal filename before inspection. Missing assemblies and disabled installations are normal: no endpoint, worker, tool, or capability is registered, and product state must not claim a connected or successful provider.

Module registration is atomic. Before any contribution becomes visible, the module ID/version must exactly match an enabled hash-pinned package installation and its executable capability set must be a subset of the package declarations with exact capability versions. Malformed assemblies, duplicate identities, package/module mismatches, undeclared capabilities, or service-registration failures expose none of the module. Disabling an installation removes all contributions for new work immediately; historical descriptors remain readable.

Product mutations address an exact `(pluginId, version)` installation. Configuration contains only manifest-declared non-secret fields and is replaced under optimistic version; unknown and secret-like fields are rejected. Removal is blocked while an account binding, active Job grant, pending Action, or retained execution reference needs the installation. Safe removal deletes mutable configuration and package availability but retains an immutable historical descriptor, so prior calls remain explainable without executable plugin code.

Runtime trust uses the states `BUILT_IN`, `TRUSTED_EXTERNAL`, `USER_APPROVED_EXTERNAL`, `UNTRUSTED`, and `DISABLED`. `UNTRUSTED` and `DISABLED` installations cannot contribute endpoints, workers, tools, capabilities, or execution. Trust changes are operator or user decisions recorded independently from provider-supplied metadata.
